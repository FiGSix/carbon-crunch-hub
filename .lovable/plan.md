# Make the live Cession Agreement the one clients actually sign

## Why the wrong version was signed

The signing flow never looks at Admin → Legal Documents. The agreement text is hardcoded in two separate places in the code:

- `supabase/functions/_shared/cession-agreement-pdf.ts` — the text typeset into the PDF
- `src/pages/ProposalAcceptance/components/TermsAndConditionsSection.tsx` — the text the client reads on screen

Both copies contain the older wording that was seeded into the database as "Cession Agreement (Revision 8)". The "Cession Agreement Rev 6" record you published on 24 Aug (about 35,800 characters) sits in the `legal_documents` table and is read by nothing except the admin list page. Every cession record in that table is currently marked inactive, and the version stamp written onto each signature is hardcoded to the string `2.0`.

So: publishing a new revision in the admin screen has no effect on signing today. That is the bug.

## What gets built

### 1. Legal Documents becomes the real source

- Admin uploads the original Cession Agreement file (PDF or Word) against a revision record. The file is stored privately and is the canonical legal text.
- On upload the system extracts the text and stores it on the record, used for the on-screen "read before you sign" panel and for a text fallback.
- Exactly one cession revision can be "Live" at a time, set by a **Set as live** button with a confirmation. Version numbers are labels only — no automatic "highest number wins", so Rev 6 can be live even though older records are numbered 8 and 9.
- The list shows a clear Live / Published / Draft / Archived state, who set it live and when.

### 2. Signing uses the live revision

- The acceptance page loads the live revision's text instead of the hardcoded component. The scroll-to-bottom gate, consent checkbox and signature step stay as they are.
- The signed PDF is assembled as: proposal pages → the live agreement's own pages spliced in verbatim from the uploaded file → the party-details and signature-confirmation pages generated by us. Nothing re-typesets the legal wording, so it reads exactly as supplied.
- The party details block (owner name, registration number, address, email, place and date of signing) is generated on its own page so the blank fill-in lines in the source file are answered without altering the original.
- The signature record stores the live revision's id, its version and title instead of the hardcoded `2.0`, so every signature is traceable to an exact document.
- The two hardcoded copies of the agreement are deleted.

### 3. Outstanding proposals

- Proposals already signed keep their original text, PDF and version stamp. Nothing is rewritten.
- Proposals that are sent but unsigned automatically pick up the live revision when the client opens the link.
- Setting a revision live shows how many unsigned proposals are affected, and offers a one-click re-notify that emails those clients that the agreement has been updated and they should review before signing.

### 4. Issues found during the end-to-end test

- `signed_pdf_url` is written as a public storage URL although `signed-agreements` is a private bucket, so the stored link returns "Bucket not found" if used directly. Store the object path and mint signed URLs on demand; backfill existing rows.
- The developer "Auth Status" widget renders on the public signing page for unauthenticated clients. Hide it outside development.
- Four `406` responses on load from anonymous reads of `clients` on the acceptance page. Route those reads through the token RPC that already serves the page.
- The proposal's own "Acceptance" block renders as an empty section; the signature only appears on the appended page. Fill or remove it.
- System size shows as a bare number with no kWp unit on the acceptance page.

## Technical notes

- New columns on `legal_documents`: `file_path`, `file_mime`, `is_live`, `set_live_at`, `set_live_by`; a partial unique index enforcing one live document per `document_type`.
- New private storage bucket `legal-documents`, admin-only write, read via service role and signed URLs.
- New security-definer function `get_live_legal_document(document_type)` so the anonymous acceptance page can read the live text and file path without exposing the whole table.
- New columns on `proposal_agreements`: `legal_document_id`, `legal_document_version`; `accepted_terms_version` populated from the record rather than the literal `2.0`.
- `generate-signed-agreement-pdf` switches from typesetting hardcoded clauses to splicing the live file's pages with `pdf-lib`, then appending the generated details and signature pages. Word uploads are converted to PDF at upload time so the splice always works against a PDF.
- `accept-proposal` resolves the live document at signing time and records its id and version.
- Re-notify reuses the existing proposal invitation email path.
